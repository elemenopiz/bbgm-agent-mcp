# Tool catalog

This is the authoritative reference for all 16 MCP tools exposed by
`bbgm-agent-mcp`, all prefixed `bbgm_`. It is generated by hand from the
actual tool registrations under `src/tools/` and the Zod schemas in
`src/domain/schemas.ts` / types in `src/domain/types.ts` — those files are
ground truth; if this document and the code ever disagree, the code wins.
The protocol surface, the public episode defaults, and a research manifest's
per-study allowlist are separate concepts; this catalog calls out each one.

## Conventions shared by every tool

**Episode scoping.** Every tool except `bbgm_create_episode` takes an
`episodeId` (a string matching `^[a-zA-Z0-9_-]+$`, 1–100 chars). An unknown
`episodeId` fails with `EPISODE_NOT_FOUND`; a known but already-ended one
fails with `ILLEGAL_ACTION` on anything but a read.

**Mutation envelope.** Every mutating tool _except_ `bbgm_create_episode`
and `bbgm_end_episode` additionally requires:

- `expectedRevision` (non-negative integer) — the revision your last
  `get_state` or mutation response reported. A stale value is rejected with
  `REVISION_CONFLICT` (which is `retryable: true` and includes the current
  revision in `details`); re-observe and retry with the fresh revision.
- `idempotencyKey` (string, 8–100 chars, `^[a-zA-Z0-9_-]+$`) — a key you
  generate per logical action attempt. Replaying the same key returns the
  cached original `MutationResult` instead of re-applying the action, so
  retries after a transient failure are safe as long as you reuse the same
  key for the same logical action. **Never** reuse a key across two
  different logical actions.

`bbgm_create_episode` doesn't need these because there is no prior revision
to be stale against. `bbgm_end_episode` doesn't need them either — ending an
episode is a one-shot terminal transition handled by `DomainService`
directly, not through the shared `runMutation` legality/rollback pipeline.

**Output envelope.** Every tool returns a plain JSON object, delivered both
as a `text` content block (`JSON.stringify`d) and as `structuredContent`,
for compatibility with clients with and without structured-output support.
On failure, the result has `isError: true` and a `content` block containing
`{ "error": { "code", "message", "retryable", "details"? } }` — never a
stack trace, filesystem path, or raw engine object.

**MCP annotations.** Tools carry one of seven annotation presets
(`src/server/errors.ts::toolAnnotations`), all with `openWorldHint: false`
(the server never reaches outside the episode's own engine):

| Preset             | `readOnlyHint` | `destructiveHint` | `idempotentHint` | Used by                                                                                                                                                                              |
| ------------------ | -------------- | ----------------- | ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `read`             | true           | false             | true             | `bbgm_get_state`, `bbgm_get_options`, `bbgm_list_checkpoints`                                                                                                                        |
| `dryRun`           | true           | false             | true             | `bbgm_evaluate_trade`                                                                                                                                                                |
| `createEpisode`    | false          | false             | false            | `bbgm_create_episode`                                                                                                                                                                |
| `createCheckpoint` | false          | false             | false            | `bbgm_create_checkpoint`                                                                                                                                                             |
| `resumeEpisode`    | false          | false             | true             | `bbgm_resume_episode`                                                                                                                                                                |
| `mutate`           | false          | true              | true             | `bbgm_execute_trade`, `bbgm_set_lineup`, `bbgm_release_player`, `bbgm_negotiate_contract`, `bbgm_sign_free_agent`, `bbgm_make_draft_pick`, `bbgm_advance`, `bbgm_restore_checkpoint` |
| `endEpisode`       | false          | true              | false            | `bbgm_end_episode`                                                                                                                                                                   |

(`mutate`'s `idempotentHint: true` reflects the idempotency-key contract
above, not that calling twice with two different keys is a no-op.)

**Error codes.** Every `DomainError` carries one of sixteen stable codes
(`src/domain/errors.ts::DomainErrorCode`), any of which any tool can
surface:

| Code                      | Meaning                                                                                                                                       | `retryable` |
| ------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | ----------- |
| `VALIDATION_ERROR`        | Input failed Zod schema validation                                                                                                            | no          |
| `EPISODE_NOT_FOUND`       | `episodeId` doesn't refer to a known episode                                                                                                  | no          |
| `REVISION_CONFLICT`       | `expectedRevision` doesn't match the episode's current revision                                                                               | yes         |
| `IDEMPOTENCY_CONFLICT`    | An idempotency key was reused for a different action than the original request                                                                | no          |
| `INFORMATION_NOT_ALLOWED` | The scenario does not permit the requested state view                                                                                         | no          |
| `ACTION_NOT_ALLOWED`      | The scenario does not permit the requested action                                                                                             | no          |
| `STEP_LIMIT`              | The scenario's maximum action-attempt budget has been reached                                                                                 | no          |
| `HORIZON_REACHED`         | The scenario's season horizon has been reached                                                                                                | no          |
| `UNSUPPORTED_CONSTRAINT`  | A declared hard constraint has no registered evaluator and the episode was rejected before starting                                           | no          |
| `UNSUPPORTED_OBJECTIVE`   | A declared soft objective has no registered evaluator and the episode was rejected before starting                                            | no          |
| `INVALID_PHASE`           | Tool isn't allowed in the episode's current `phase` (e.g. most roster mutations during `draft`, or `bbgm_make_draft_pick` outside `draft`)    | no          |
| `ILLEGAL_ACTION`          | Legal in this phase, but this specific input isn't (unowned player/pick, duplicate lineup entries, unknown checkpoint, episode already ended) | no          |
| `INVARIANT_VIOLATION`     | A hard invariant failed after the mutation ran; the mutation was rolled back to its pre-mutation snapshot                                     | no          |
| `ENGINE_ERROR`            | An unexpected/non-`DomainError` failure, normalized so no raw engine internals leak                                                           | no          |
| `TIMEOUT`                 | An unresponsive worker call exceeded the configured deadline; the episode is quarantined until resumed                                        | yes         |
| `RESOURCE_LIMIT`          | A bounded resource limit was hit — currently the ≤50 concurrent active episodes cap in `EpisodeManager`                                       | no          |

Every tool below can, in principle, also fail with `VALIDATION_ERROR`,
`EPISODE_NOT_FOUND`, and `ENGINE_ERROR`; the per-tool lists below cover only
the _additional_, tool-specific codes worth knowing about.

**Views, targets, and actions used across tools.**

- `GetStateViewName` (10 values): `overview`, `roster`, `finances`,
  `standings`, `schedule`, `free_agents`, `draft`, `transactions`,
  `objectives`, `constraints`.
- `AdvanceTarget`: `next_game`, `next_decision`, `days`, `games`, `week`,
  `month`, `one_pick`, `phase`, `season_end`, and named upstream milestones
  (`until_all_star_game`, `until_trade_deadline`, `until_playoffs`,
  `until_end_of_round`, `until_end_of_play_in`, `through_playoffs`,
  `until_draft`, `until_next_pick`, `until_resign_players`,
  `until_free_agency`, `until_preseason`, `until_regular_season`). A
  scenario can restrict these with `allowedAdvanceTargets`; the public
  episode preset permits the complete list.
- Checkpoint tools: `create_checkpoint`, `list_checkpoints`,
  `restore_checkpoint`.

## `bbgm_create_episode`

**Kind:** mutating, not destructive (`createEpisode` annotation preset — it
creates rather than changes existing state).

**Purpose:** Create an isolated, seeded research episode running in its own
engine/worker and return its initial normalized overview state. Must be
called before any other `bbgm_*` tool for that episode.

Public episodes use the complete typed BBGM pacing surface with a 300-step and
2-season budget. The caller cannot rewrite that policy through the MCP input
schema; a trusted research caller can supply a narrower scenario policy.

**Inputs:**

| Field            | Type                                                            | Notes                                                                                                                                                                        |
| ---------------- | --------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `scenarioId`     | string, 1–100 chars                                             | Research scenario identifier; grouped in trajectory logs                                                                                                                     |
| `seed`           | string, 1–100 chars                                             | Episode seed; exact state-hash reproduction additionally requires the same pinned engine, wrapper/runtime, initial conditions, and normalized state-changing action sequence |
| `userTeamId`     | non-negative int                                                | Default `0`. Team controlled by the agent                                                                                                                                    |
| `startingSeason` | int, 1900–2200                                                  | Default `2026`                                                                                                                                                               |
| `constraints`    | `{ hard: ConstraintDefinition[], soft: ObjectiveDefinition[] }` | Optional. Hard constraints and soft objectives this episode is scored against (each definition is `{ code, description, weight?, targetValue? }`, max 50 each)               |
| `scenarioPolicy` | not a public MCP input                                          | Public episodes use the complete typed pacing preset with a 300-step and 2-season budget; trusted research callers may inject a narrower policy through the evaluation API.  |

**Output:** an `overview` `LeagueStateView` (`schemaVersion`, `episodeId`,
`revision: 0`, `stateHash`, `season`, `phase`, `status: "active"`, `userTeam`,
`rosterCount`, `rosterExcerpt` (top 5 by `overall`), `ownedPickCount`,
`constraintsSatisfied`, `legalActionCategories`, `nextDecision`).

**Notable errors:** `RESOURCE_LIMIT` if 50 episodes are already active.

Public MCP episodes receive the full typed advance policy, including
`week`, `month`, and `one_pick`. The evaluated agent cannot rewrite the
`scenarioPolicy`; a research manifest or trusted direct caller can narrow the
targets for a particular study.

## `bbgm_resume_episode`

**Kind:** lifecycle, non-destructive.

**Purpose:** Rehydrate an active, ended, or quarantined episode from its
durable metadata and current snapshot after a process restart. The recorded
engine name, version, and commit must match the currently configured engine.
If the episode was quarantined after a worker failure, a successful resume
returns it to `active` status.

**Inputs:** `episodeId`.

**Output:** the current `OverviewView`.

## `bbgm_get_state`

**Kind:** read-only.

**Purpose:** Read a bounded, paginated slice of normalized league state.
Never advances or mutates. Choose the narrowest `view` for your question
rather than defaulting to `overview` for everything.

**Inputs:** `episodeId`; `view` (one of the 10 `GetStateViewName` values);
`cursor` (non-negative int, optional pagination offset); `limit` (positive
int, max 50, optional — server-bounded default when omitted); `teamId`
(non-negative int, optional, **only meaningful for `view="roster"`**) —
reads that team's public roster instead of the user's own. This is how an
agent inspects a prospective trade partner's actual assets before proposing
anything: rosters are public information in ordinary play, unlike the
opponent's hidden trade-acceptance valuation (which `bbgm_evaluate_trade`
deliberately does not expose). Reading another team's roster requires the
episode to still be active — after `bbgm_end_episode`, only the user's own
(cached) roster stays readable.

**Output:** one of 10 discriminated-union shapes (`LeagueStateView`), keyed
by `view`. All share a common envelope
(`schemaVersion`, `episodeId`, `revision`, `stateHash`, `season`, `phase`).
List-bearing views (`roster`, `standings`, `schedule`, `free_agents`,
`draft` prospects, `transactions`) additionally carry a `page`
(`{ nextCursor?, hasMore, totalCount, limit }`) so a large league is never
returned in one call. `roster` also carries `teamId`, naming whose roster
is being returned (the user's own team unless `teamId` was passed).
`overview` carries a `rosterExcerpt` and summary counts instead of a full
roster; `finances`, `objectives`, and `constraints` are unpaginated
(bounded by construction).

For `view="draft"`, `prospects` is paginated and `draftPicks` is the complete
current-owner ledger (including opponent-held picks), sorted by season, round,
and draft-pick ID. `ownedPicks` remains the user's convenience subset used by
trade validation and the research metrics. Pick IDs are discoverable here;
proposal legality still comes from `bbgm_evaluate_trade`.

**Notable errors:** `ILLEGAL_ACTION` if `teamId` names another team and the
episode has already ended (that team's live state is no longer readable
once its engine is closed; the user's own final roster remains readable
regardless).

## `bbgm_get_options`

**Kind:** read-only.

**Purpose:** List legal action categories and bounded candidate IDs for the
current phase, stamped with the revision they were generated at. Options
can go stale after any mutation — re-fetch after advancing or mutating
before acting on a previously returned option.

**Inputs:** `episodeId` only.

**Output:** `{ episodeId, revision, options: EngineOption[] }`, where each
option is an open-ended `{ type: string, ...fields }` record (e.g.
`{ type: "advance", target: "next_game" }`, `{ type: "sign_free_agent",
pid, name }`) — the option shape is intentionally engine-defined rather than
tightly typed per option kind. This response is revision-stamped but does not
carry a `stateHash`; use `bbgm_get_state` when a state hash is required.

**Notable errors:** requires an _active_ episode (`ILLEGAL_ACTION` if
already ended, unlike `bbgm_get_state` which can still read an ended one).

---

## `bbgm_evaluate_trade`

**Kind:** read-only (dry run).

**Purpose:** Check a proposed trade's legality, roster/payroll effects, and
opponent acceptance where the engine can determine it, without mutating
anything. Safe to call as many times as needed while exploring offers; does
not consume an `idempotencyKey`. Always call this before
`bbgm_execute_trade`.

**Inputs:** `episodeId`; `proposal: TradeProposal` —
`{ otherTeamId, offered: TradeAsset[], requested: TradeAsset[] }` where a
`TradeAsset` is `{ type: "player", pid }` or `{ type: "draft_pick", dpid }`
(max 20 assets each side).

**Output:** `TradeEvaluation` — `{ legal, acceptedByOtherTeam: boolean |
null, reasons: string[], payrollDelta, rosterSizeDelta, assetsExchanged }`.
`acceptedByOtherTeam` is `null` when the trade isn't even legal, so
acceptance couldn't be evaluated.

---

## `bbgm_execute_trade`

**Kind:** mutating.

**Purpose:** Execute a previously evaluated, legal trade. Not allowed during
the `draft` phase.

**Inputs:** mutation envelope (`episodeId`, `expectedRevision`,
`idempotencyKey`) + `proposal: TradeProposal` (same shape as
`bbgm_evaluate_trade`).

**Output:** `MutationResult` (see shared shape below).

**Notable errors:** `INVALID_PHASE` during `draft`; `ILLEGAL_ACTION` if
`otherTeamId` is the user's own team, or an offered player/pick isn't
actually owned by the user; `INVARIANT_VIOLATION` (with rollback) if the
resulting state fails a hard constraint (e.g. cap compliance under a hard
cap, roster size out of `[10, 15]`).

---

## `bbgm_set_lineup`

**Kind:** mutating.

**Purpose:** Set the roster's depth-chart order (playing-time priority).
Not allowed during the `draft` phase.

**Inputs:** mutation envelope + `order: number[]` (1–20 player IDs, must
contain **exactly** the current roster's player IDs, most-preferred first).

**Output:** `MutationResult`.

**Notable errors:** `ILLEGAL_ACTION` if `order` has duplicates, is missing a
current roster player, or includes a player not on the roster.

---

## `bbgm_release_player`

**Kind:** mutating.

**Purpose:** Waive a player from the user's roster to free agency. Not
allowed during the `draft` phase.

**Inputs:** mutation envelope + `pid` (non-negative int).

**Output:** `MutationResult`.

**Notable errors:** `ILLEGAL_ACTION` if `pid` isn't on the user's roster.

---

## `bbgm_negotiate_contract`

**Kind:** mutating.

**Purpose:** Extend or renegotiate the contract of a player already on the
user's roster. Not allowed during the `draft` phase.

**Inputs:** mutation envelope + `pid` + `amount` (positive number, max 500 —
annual salary in millions) + `years` (int, 1–7).

**Output:** `MutationResult`.

**Notable errors:** `ILLEGAL_ACTION` if `pid` isn't on the user's roster.

---

## `bbgm_sign_free_agent`

**Kind:** mutating.

**Purpose:** Sign an available free agent to the user's roster on the given
contract terms. Not allowed during the `draft` phase.

**Inputs:** mutation envelope + `pid` + `amount` + `years` (same contract
terms shape as `bbgm_negotiate_contract`).

**Output:** `MutationResult`.

**Notable errors:** `ILLEGAL_ACTION` if `pid` isn't currently a free agent.

---

## `bbgm_make_draft_pick`

**Kind:** mutating.

**Purpose:** Select an available prospect with the user's next owned draft
pick. Only allowed during the `draft` phase.

**Inputs:** mutation envelope + `pid` (prospect ID to select).

**Output:** `MutationResult`.

**Notable errors:** `INVALID_PHASE` outside `draft` (this is the one tool
with a `requiredPhase` rather than a `disallowedPhases` list);
`ILLEGAL_ACTION` if `pid` isn't an available prospect, or no owned draft
picks remain.

---

## `bbgm_advance`

**Kind:** mutating.

**Purpose:** Advance simulated time by one of the complete typed targets below.
Advancement stops at a decision point requiring GM input (e.g. a pending draft
pick) even if the requested target has not been reached; the returned `events`
include an `advance_complete`-style entry explaining why it stopped.

**Inputs:** mutation envelope + `target: AdvanceTarget` + optional `count`
(int, 1–30). `count` is **required** when `target` is `"days"` or
`"games"`; it is optional and has no effect for the fixed-semantics targets.

| `target`               | Behavior                                                                                                                                 |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `next_game`            | Step until one user-team game is played, the next phase is reached, a pending decision blocks progress, or the internal bound is reached |
| `next_decision`        | Use the bounded phase-step controller; stop at a pending user decision or phase transition                                               |
| `days`                 | Advance an explicit number of days (`count`, max 30)                                                                                     |
| `games`                | Advance until `count` user-team games are played (`count`, max 30), subject to pending decisions and the internal bound                  |
| `week`                 | Invoke upstream's fixed week pacing operation                                                                                            |
| `month`                | Invoke upstream's fixed month pacing operation                                                                                           |
| `one_pick`             | Invoke upstream's fixed one-pick pacing operation; it never selects a player for the user                                                |
| `phase`                | Advance to the next league phase using the bounded phase-step controller                                                                 |
| `season_end`           | Advance until the season changes, normally reaching the next preseason                                                                   |
| `until_all_star_game`  | Advance to the All-Star milestone, with a bounded phase-step fallback when the upstream marker is absent                                 |
| `until_trade_deadline` | Advance to the trade-deadline milestone, with the same bounded fallback                                                                  |
| `until_playoffs`       | Advance to the playoffs milestone                                                                                                        |
| `until_end_of_round`   | Advance through the current playoff-round boundary                                                                                       |
| `until_end_of_play_in` | Advance through the play-in boundary                                                                                                     |
| `through_playoffs`     | Advance through the playoffs boundary, potentially crossing into the next season                                                         |
| `until_draft`          | Advance to the draft phase                                                                                                               |
| `until_next_pick`      | Advance until the user's next owned pick requires `bbgm_make_draft_pick`                                                                 |
| `until_resign_players` | Advance to the resigning phase                                                                                                           |
| `until_free_agency`    | Advance to free agency; headless resign confirmation is treated as an explicit proceed request                                           |
| `until_preseason`      | Advance to preseason                                                                                                                     |
| `until_regular_season` | Advance to the regular season                                                                                                            |

All targets are bounded by the episode's step/horizon policy and stop safely
when a mandatory user decision is pending. The upstream automatic `untilEnd`
draft-completion action is intentionally not part of `AdvanceTarget`, because
it could make a mandatory draft choice on the agent's behalf. `simToGame` and
other UI/editor operations are likewise not exposed.

**Output:** `MutationResult`.

---

## `bbgm_create_checkpoint`

**Kind:** non-destructive lifecycle.

**Purpose:** Persist an opaque checkpoint of the current episode state. The
checkpoint ID is server-generated and never exposes a filesystem path.

**Inputs:** `episodeId`.

**Output:** `{ checkpoint: Checkpoint }`.

---

## `bbgm_list_checkpoints`

**Kind:** read-only.

**Purpose:** List the opaque checkpoints already created for an episode.

**Inputs:** `episodeId`.

**Output:** `{ checkpoints: Checkpoint[] }`.

---

## `bbgm_restore_checkpoint`

**Kind:** mutating.

**Purpose:** Restore a previously created checkpoint. The league's simulated
state may move backward, but the episode revision always advances and the
operation is retry-safe through the standard mutation envelope.

**Inputs:** `episodeId`, `checkpointId` (1–100 chars),
`expectedRevision`, and `idempotencyKey`.

**Output:** `{ mutation: MutationResult }`.

**Notable errors:** `ILLEGAL_ACTION` for an unknown checkpoint ID.

---

## `bbgm_end_episode`

**Kind:** mutating, terminal (`endEpisode` annotation preset:
`destructiveHint: true`, `idempotentHint: false` — calling it twice on the
same episode fails the second time, since the episode no longer exists as
active).

**Purpose:** Finalize an episode: flush the trajectory log, optionally
export a final checkpoint, compute terminal metrics, and terminate the
episode's worker. No further mutations are possible on this `episodeId`
afterward; the episode remains permanently readable via `bbgm_get_state`.

**Inputs:** `episodeId` + `exportFinalSnapshot` (boolean, default `true`).
No `expectedRevision`/`idempotencyKey` — see "Mutation envelope" above.

**Output:** `EndEpisodeResult` — `{ episodeId, finalState: OverviewView,
terminalMetrics: { episodeId, seasonsCompleted, finalRecord: {won, lost},
hardConstraintViolations, transactionCount }, snapshotCheckpointId? }`.

---

## Shared output shape: `MutationResult`

Every mutating tool except `bbgm_create_episode` and `bbgm_end_episode`
returns this shape:

```ts
type MutationResult = {
  episodeId: string;
  previousRevision: number;
  revision: number; // previousRevision + 1 on success
  stateHash: string; // sha256, post-mutation
  appliedAction: Record<string, unknown>; // normalized, e.g. { type: "release_player", pid }
  events: EngineEvent[]; // engine-defined, open-ended
  warnings: string[]; // unsatisfied SOFT constraints only (hard failures throw instead)
  nextDecision: string;
  stateSummary: OverviewView; // so callers rarely need a follow-up bbgm_get_state
};
```
